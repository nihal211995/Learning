Three rules that hold across every product

1. Safety outranks everything

Safety, fraud and legal signals route to humans before any model reply.

2. AI proposes, rules and people decide

Deterministic limits and human approval gate every consequential action.

3. Right data source for the job

RAG for documents, semantic layer + SQL for metrics, APIs for live state and actions, MCP to wrap many systems.

Shared architecture

All six products reuse the same five layers. What differs is the workflow, prompts, tools, policy corpus, rules and metrics.

1 · Interface and intent
  • Channels: app chat, host app, agent desktop, Slack/portal for leaders.
  • Authenticate first; attach identity, locale and reservation context.
  • Classify intent and risk before any reasoning.
  • Ask one clarifying question when the answer would change.
2 · Orchestration and decisions
  • Default: single agent with tools. Add agents only for different permissions, isolated context or independent verification.
  • Workflow graph with step limits and explicit state.
  • Ordered rules: safety, identity, policy, limits, confidence.
  • Outputs: resolve, clarify, investigate or escalate.
3 · Knowledge and data
  • RAG for policies, macros, definitions (unstructured, changes often).
  • Semantic layer + SQL for governed metrics.
  • REST APIs for live state and actions.
  • MCP as a standard wrapper when many systems must be exposed.
4 · Model layer
  • Tiers: primary, lightweight, embedding, reranker, specialised classifiers.
  • Route by task to control cost and latency; keep fallbacks.
  • Manage context: retrieve, summarise, cap tool output.
  • Pin model versions; re-run evals on every upgrade.
5 · Execution, guardrails, evaluation
  • Least-privilege tools, idempotency, pre-action validators.
  • PII redaction, prompt-injection defence, grounding and citations.
  • Golden sets, A/B tests, drift and cost monitoring.
  • Human escalation with a case file; kill switch.

Product 1 · Mode 1 → 2

Guest Self-Service Resolution Agent

Guests resolve cancellations, refunds, double charges and changes without waiting for a person.
Who it serves: Guests on the app or web. Highest volume, lowest average complexity.

Blue = retrieval · purple = LLM · green = tool/API · amber = guardrail · red = human.

Tap a box to see what it does.
  1. User / systemGuest messagein-app chat · verified session

    Guest writes in the app. Identity, locale and active reservation are attached automatically.

  2. GuardrailAccess control & PIIguest scope · own reservations

    Verifies the guest may act on this reservation; limits tool scopes; redacts PII before logging.

  3. LLM reasoningTriage: intent + risklight model + safety rules

    Classifies intent (cancel, refund, double charge, change) and risk. Safety, fraud and legal language shortcut to humans.

  4. LLM reasoningOrchestrator (workflow graph)plan · state · step limit

    Runs a fixed workflow for refunds and cancellations; allows bounded investigation. Keeps case state.

  5. Data retrievalRAG · policycancellation · refund · fees

    Retrieves region- and date-specific policy chunks (vector search + rerank) with source IDs.

  6. Data retrievalAPI tools (MCP optional)booking · payments · host status

    Reads live reservation, payment ledger and host status through scoped APIs.

  7. Data retrievalSQL / API · historyprior contacts · refunds issued

    Looks up earlier contacts and refunds to spot repeats and abuse patterns.

  8. LLM reasoningDecision enginerules + AI judgement + confidence

    Deterministic business rules (eligibility, limits) combine with LLM judgement on edge cases and a calibrated confidence score. The model never sets amounts or overrides policy.

  9. Tool / APIA · Resolve automaticallyvalidated refund / cancel / change

    Pre-action validator checks permissions, limits and duplicates; API runs with an idempotency key; result verified; guest told.

  10. GuardrailB · Clarifyask one targeted question

    Asks for the single missing detail (e.g. which booking, which charge) and re-decides.

  11. LLM reasoningC · Investigate furthermore tools · bounded steps

    Checks processor status or host messages within a step cap, then re-decides.

  12. HumanD · Escalate to humancase file + reason code

    Hands over summary, evidence, policy cited, what was tried and why the AI stopped.

  13. HumanHuman support agent receives the full case file

    Specialists take escalated and directly routed cases; their decisions become labelled data.

Guardrails
  • Auto-approve only inside deterministic limits and only after identity is verified.
  • Every action needs an idempotency key and a post-action verification read.
  • Safety, fraud or legal wording shortcuts to a human before any model reply.
  • Replies must cite policy or ledger; uncited claims are blocked.

  • Escalation quality: share of handoffs where the human needed no re-asking.
  • CSAT matched to similar human-handled cases, plus cost per resolved case.

  8. LLM reasoningDecision enginerules + AI judgement + confidence

  10. GuardrailB · Clarifywhich payout / listing?

Product 3 · Mode 3 (assist only)

Safety & Trust Triage Agent

AI helps spot and prepare urgent cases fast. It never decides and never closes a safety case.
Who it serves: Guests and hosts who may be in danger or reporting serious violations. Lowest volume, highest stakes.

Blue = retrieval · purple = LLM · green = tool/API · amber = guardrail · red = human.

Tap a box to see what it does.
  1. User / systemGuest / host messagein-app chat · call-back option

    Any message or call transcript that may signal danger.

  2. GuardrailAccess control & PIIminimum data · location consent

    Shares only the minimum data with responders; location used with consent or emergency rules.

  3. LLM reasoningSeverity triagerules + fast classifier · recall first

    Hard rules plus a high-recall classifier assign severity. Tuned so urgent cases are almost never missed.

  4. LLM reasoningOrchestrator (fixed workflow)assist only · human decides

    Mostly deterministic. The AI summarises and prepares; it never decides outcomes.

  5. Data retrievalRAG · safety protocolsplaybooks · escalation tiers

    Retrieves the approved safety playbook for the severity and region.

  6. Data retrievalAPI tools · contextbooking · location · prior flags

    Reads booking, host/guest history and prior safety flags for the responder.

  7. Tool / APIResponder pagingon-call safety team · queue API

    Pages the right on-call team and opens a priority case.

  8. LLM reasoningSeverity enginerules + classifier · recall first

    Assigns severity. Any urgent or uncertain-but-possibly-urgent signal triggers immediate human handoff; the AI never closes a safety case.

  9. User / systemA · Resolve automaticallyNOT PERMITTED

    AI never resolves a safety case.

  10. GuardrailB · Clarify (minimal)only if it speeds handoff

    At most one short question (e.g. location) while the human is already being paged.

  11. LLM reasoningC · Gather contextsummary for the responder

    Prepares a concise case summary and relevant history for the responder.

  12. HumanD · Immediate human handoffpage responder · summary

    Pages specialised responders at once with severity, summary and reason code.

  13. HumanSpecialised safety responders take over

    Trained responders decide actions; AI shows only pre-approved safety guidance meanwhile.

Product 4 · Mode 2 (human approves)

Dispute & Reimbursement Resolution Agent

AI assembles evidence and recommends an outcome. A trained human approves.
Who it serves: Guests and hosts in damage, 'not as described' and reimbursement claims. Evidence-heavy, money at stake.

Blue = retrieval · purple = LLM · green = tool/API · amber = guardrail · red = human.

Tap a box to see what it does.
  1. User / systemClaim submittedguest or host · evidence upload

    A 'not as described' or damage claim with photos, messages and amounts.

  2. GuardrailAccess control & PIIparty-scoped · both sides' evidence

    Each party sees only their own submissions; the case file is visible to reviewers.

  3. LLM reasoningTriage: claim typenot-as-described · damage · other

    Classifies claim type, value and complexity; routes high-risk claims to humans.

  4. LLM reasoningOrchestrator (evidence workflow)assemble · analyse · recommend

    Runs an evidence workflow: gather, check consistency, compare with policy, draft a recommendation.

  5. Data retrievalRAG · dispute policyguarantee · damage terms

    Retrieves guest-refund and host-damage policy for the case region and date.

  6. Data retrievalMCP / API · evidencemessages · photos · listing

    Pulls messages, photos, listing description and check-in/out records from several systems.

  7. Data retrievalSQL / API · paymentscharges · refunds · prior claims

    Reads transaction and prior-claim history for both parties.

  8. LLM reasoningDecision enginerules + AI judgement + confidence

    Deterministic business rules (eligibility, limits) combine with LLM judgement on edge cases and a calibrated confidence score. The model never sets amounts or overrides policy.

  9. Tool / APIA · Auto-resolve (narrow)tiny, clear-cut amounts only

    Only very small, unambiguous claims inside strict limits; everything else needs a human.

  10. GuardrailB · Request more evidenceask either party

    Asks a party for missing photos, dates or details.

  11. LLM reasoningC · Analyse evidenceconsistency · timeline · policy

    Checks consistency across messages, photos and timeline; drafts recommendation with citations.

  12. HumanD · Human approvalrecommendation + evidence pack

    A trained reviewer approves, edits or rejects the recommended outcome.

  13. HumanDispute reviewer approves the outcome

    The AI recommends; a human decides and owns the outcome.

Worked examples

The same decision framework, three different outcomes. All numbers are illustrative.

Example 1 · Guest double charge (P1)
  1. Guest: 'I was charged twice.' Gateway verifies identity and loads reservation r_987.
  2. Triage: intent = duplicate_charge, risk = low. No safety or fraud signal.
  3. Parallel retrieval: refund-duplicate policy (RAG), payment ledger and booking (APIs).
  4. Decision: ledger shows two identical charges 40 seconds apart; $42 is under the $50 auto-limit; policy is clear; confidence 0.93.
  5. Validator checks permission, limit and duplicate refund; API runs with an idempotency key; a verification read confirms.
  6. Reply cites the policy and the ledger row. Logged for evaluation; a 7-day re-contact check scores the outcome.
Example 2 · Safety message (P3)
  1. Guest writes a message that may signal harassment during a stay.
  2. Rules plus a high-recall classifier flag severity 'high' (confidence 0.71, below auto-comfort).
  3. Low confidence routes up: the case is paged to the safety responder queue at once.
  4. The model writes a short factual summary and attaches booking and history; it does not decide anything.
  5. The user sees only pre-approved safety guidance until the responder joins.
  6. The responder decides actions; the case feeds the missed-urgent evaluation set.
Example 3 · Leadership question (P6)
  1. Leader: 'Why did contact rate rise in Brazil last month?' SSO role limits access to BR and MX.
  2. Triage: diagnose question; metric contact_rate; scope BR; period last month.
  3. Retrieval: contact_rate definition (contacts / completed bookings) and recent incidents and releases.
  4. SQL on the semantic layer decomposes the change by case type, channel and language; validator enforces read-only and limits.
  5. Verifier reconciles totals with the certified dashboard; the cancellation share jumps; a 12 Oct policy change overlaps.
  6. Answer cites definition, query IDs and as-of time, and states this is association, not proof of cause; flags for analyst if confidence is low.

Glossary

18 terms. Click to expand.

RAG (retrieval-augmented generation)

The model answers using passages retrieved from a knowledge base at request time, instead of relying only on its training. Best for policies and documents that change.

MCP (Model Context Protocol)

An open standard for exposing tools and data to AI applications. Think of a universal adapter that wraps many internal systems behind one interface.

REST API

A standard way for software to read or change data over HTTP. Best for live state and for taking actions (refund, cancel).

Semantic layer

A governed catalogue of business metrics and dimensions with one definition each. Lets the AI call 'contact rate' rather than invent SQL.

Context window

The maximum number of tokens (input plus output, in most APIs) a model can handle in one request.

Token

A chunk of text, roughly three-quarters of an English word. Cost and limits are measured in tokens.

Embedding

A numeric vector that represents the meaning of text so similar texts sit close together; used for search.

Reranker

A model that re-scores retrieved passages against the query so the best few go to the LLM.

Orchestrator

The control loop that decides the next step: call a tool, ask the user, retrieve, or escalate.

Tool calling

The model outputs a structured request to run a function; your code runs it and returns the result.

Guardrail

A deterministic check (limits, permissions, validation) that constrains what the AI may say or do.

Idempotency key

A unique ID that makes a repeated request safe: the same refund submitted twice happens once.

Human-in-the-loop (HITL)

A person reviews, approves or performs the consequential step; the AI assists.

Confidence routing

Using a calibrated score to decide whether to act, ask, or escalate.

Prompt injection

Untrusted text (a message, a photo caption) trying to give the model new instructions. Treat all user content as data.

PII redaction

Removing or masking personal data before it is logged, retrieved or shown.

Golden set

A curated set of cases with known right answers, used to evaluate every change before release.

Fine-tuning

Further training a model on your data. Different from changing prompts or payloads; rarely needed here beyond small classifiers.
