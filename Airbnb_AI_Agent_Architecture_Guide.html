Two use cases, one architectural pattern

Both systems share the same five-layer skeleton. What differs is the risk profile: UC1 reads data and explains it; UC2 reads data and changes things for real customers.

Use Case 1

Internal Leadership Self-Service Chatbot

Objective: leaders ask business questions in natural language and get governed, cited answers about metrics, drivers and operations.

  • "What was our support contact rate last month?"
  • "Which markets have the highest repeat-contact rates?"
  • "What is driving the increase in complaints?"

Must do: identify intent · retrieve from warehouse, dashboards, docs · generate SQL on a semantic layer · return tables/charts/summaries · show sources, lineage and metric definitions · enforce access control.

Character: read-only · accuracy and traceability matter most · wrong numbers erode trust.

Use Case 2

Customer Support AI Agent

Objective: understand, classify, investigate and resolve support cases; escalate to humans only when needed and say why.

  • "I was charged twice for the same booking."
  • "My host has not responded to my messages."
  • "I have an urgent safety concern during my stay."

Must do: classify intent · pull customer, booking and payment context · retrieve policy · decide resolve / investigate / escalate · execute permitted actions via APIs · explain escalations.

Character: read + write · safety and money at stake · wrong actions harm people.

Three ways a support case can be handled

Mode 1

AI-led self-service resolution

Clear intent, policy clearly covers it, action is within limits, evidence is consistent, confidence is high. The agent acts and confirms.

Example: cancel a reservation that is within the free-cancellation window.

Mode 2

AI-led investigation, then human escalation

The agent gathers evidence, checks policy, attempts resolution, and hands a complete case file to a human when it hits a limit (ambiguity, amount, policy gap).

Example: "property not as described" refund needing photos and host response.

Mode 3

Direct routing to specialized human support

Risk is high enough that the AI should not try to resolve: safety, suspected fraud or account takeover, legal threats. Route immediately, with a brief summary.

Example: "There is a safety concern at the property right now."

Decision framework: resolve, investigate, or escalate?

Try it. Toggle the signals a real case might carry and see which path a rules-first decision engine would choose. Rules are ordered — the first rule that matches wins, and safety always outranks everything. Thresholds here are illustrative.

1User Interface & Intent Understanding

The front door. Its job is to turn free text into a structured, routable request — and to catch risk before any reasoning starts.

Point 1

Chat interface that carries context for free

Users talk to the agent in a chat surface; the surface should attach everything it already knows so the model never asks for it.

UC1: authenticated internal portal or chat app; the user's identity, role and permitted markets travel with every message.
UC2: in-app help chat; session already carries the verified user, active reservation and locale — don't ask "what's your booking code?" if it's known.
Point 2

Extract intent, entities and context

An LLM reads the message and emits a small JSON object (structured output): intent, entities, urgency/sentiment, language.

UC1: intent = diagnostic "why"; metric = contact rate; geography = India; period = last month.
UC2: intent = duplicate_charge; entity = this reservation; urgency = normal; sentiment = frustrated.
Point 3

Classify into a taxonomy — safety first

Use layered classification: deterministic rules and keyword/safety detectors first, then a cheap model against a fixed taxonomy, with a confidence score. Low confidence or "unknown" falls to a safe default, never a guess.

Rules for hard-risk phrasesLightweight LLMEmbedding nearest-neighbourSmall trained classifier
Point 4

Route with a table, not a hunch

A routing table maps (intent, risk, confidence) to a workflow, tool set or queue. The LLM proposes the label; the table — owned by the business — decides where it goes.

UC1 routes: metric lookup · driver diagnosis · documentation question · out-of-scope/refuse.
UC2 routes: self-service workflow · investigation workflow · direct specialist queue (safety, fraud, legal).

2Agent Orchestration & Decision Making

The control loop. It decides what to do next, calls the right tool, remembers what happened and knows when to stop.

Point 1

Decide the next action each step

At every step the orchestrator picks one of five actions, observes the result, and repeats — with a hard step limit.

RetrieveNeeded fact is missing (policy text, metric definition, order record)
ActDecision made, action permitted and validated
ClarifyRequest is ambiguous and the answer changes the result
AnswerEvidence is sufficient and grounded
EscalateRisk, policy gap, low confidence, or step budget spent
Point 2

Single agent vs multi-agent — what do you actually need?

A multi-agent design adds coordination cost, latency and failure modes. Start with one orchestrating agent plus specialized tools; split into separate agents only when you need different permissions, isolated context, or independent verification.

UC1 verdict: single agent with tools (metric catalog, SQL, RAG, chart) is sufficient. Optional second pass: a separate "verifier" step that re-checks numbers.
UC2 verdict: single resolution agent on a deterministic workflow graph is sufficient. Justified split: a separate safety/risk triage step with its own permissions that can pre-empt everything.
Point 3

Tool calling inside workflow orchestration

With tool / function calling the model proposes a typed call; the orchestrator validates it and executes it. Use agentic loops where the path is unknown (investigation) and fixed workflow graphs where it must be predictable (refund, cancellation).

LangGraphOpenAI Agents SDKClaude Agent SDKGoogle ADKPlain application code

Frameworks are conveniences, not requirements; a state machine in plain code is often enough for UC2's core flows.

Point 4

State and memory across turns

Memory lives outside the model. Keep a compact case state object (what is known, what was done, open questions), recent turns verbatim, a rolling summary, and long-term facts fetched on demand — not stuffed into every prompt.

UC1: remember the active metric, filters and time range so "and for Brazil?" works.
UC2: persist the case file so a human receives the full history, evidence and reason for escalation.
Rule of thumb: add an agent only when it removes a real constraint (permissions, context isolation, parallelism, independent checking). "More agents" is not an architecture goal.

3Knowledge Retrieval & Data Connectivity

How the agent gets facts. The core design skill is picking the right access method for each kind of information.

Point 1

RAG — for knowledge in unstructured text

Why: models don't know your current policies or metric docs, and you can't paste a whole knowledge base into every request. RAG fetches only the relevant passages and lets the model cite them.

  • Chunk documents by heading/section (roughly a few hundred tokens) and attach metadata: region, effective date, policy version, audience.
  • Embed each chunk; store in a vector database.
  • Retrieve with hybrid keyword + semantic search, filter by metadata, then rerank top candidates.
  • Pass the top few chunks, with source IDs, into the prompt.

Not RAG: exact facts (a booking's status, a charge amount, a metric value) belong in databases and APIs. Retrieval by similarity can return a plausible but wrong number.

Point 2

MCP — a standard plug for tools and data

The Model Context Protocol is an open standard where an MCP server advertises tools (actions), resources (data) and prompts in a uniform, self-describing way. Any MCP-capable agent can discover and call them.

MCP vs a traditional API integration: a REST API is the interface of one system; each agent needs custom glue code for it. An MCP server wraps systems behind one discoverable, typed interface so many agents reuse it. MCP doesn't replace APIs — it usually sits in front of them.

Governance still applies: allow-list servers, scope credentials per user, log every call, and treat third-party servers and tool outputs as untrusted input (prompt injection).

Point 3

Direct SQL, APIs and the semantic layer

The workhorses for structured facts.

  • Warehouse + SQL generation for metrics. Generate queries against a semantic layer / metrics catalog (governed definitions of "contact rate", approved joins) instead of raw tables.
  • REST APIs for live, transactional state and for actions (refund, cancel) — deterministic, permissioned, auditable.
  • Internal docs / knowledge bases via RAG; dashboards via a BI API or MCP wrapper so answers reuse certified numbers.
Point 4

Examples by use case

UC1: definitions of "repeat contact" and release notes → RAG · "contact rate by market, last month" → semantic layer + SQL · "latest certified Support dashboard numbers" → BI via MCP/API · lineage and freshness → catalog lookup.
UC2: refund and cancellation policy → RAG (filtered by region/date) · reservation and payment ledger → internal APIs · issuing a refund → API with limits and idempotency key · past similar cases → search over redacted case summaries.

Why not just stuff everything into a huge context window?

Nominal context windows are large (about a million tokens for several current models), but passing an entire knowledge base on every request is slower, costlier, and typically less accurate because relevant text is diluted among distractors. RAG sends the few passages that matter and makes citations possible. See Section 4 for the token math.

4LLM & Model Architecture

A production agent is a small portfolio of models, each matched to a job — not one giant model for everything.

1 · Primary LLM

Reasoning & response

Understands nuance, plans multi-step work, picks tools, writes grounded answers. Highest quality, highest cost per call — use it where judgement matters.

2 · Lightweight LLM

Classify, route, summarize

Fast and cheap; handles intent labels, safety pre-screens, summaries, formatting. Often 10–50× cheaper per token than the primary model.

3 · Embedding model

Text → vectors

Turns documents and queries into vectors so semantically similar text lands close together. Powers retrieval; not a generative model.

4 · Reranking model

Sharpen retrieval

Scores each (query, passage) pair jointly; reorders the top 20–50 retrieved chunks so the best 3–5 reach the prompt.

5 · Specialized models

Predict, don't chat

Forecasting (contact volume), anomaly detection, classifiers (escalation risk), PII detectors. Cheaper, testable, and better than an LLM at numeric prediction.

Principle

Match model to task

Use the smallest model that clears your evaluated quality bar on that task. Re-test when providers release new versions.

Context window, explained

What it is

The context window is the maximum number of tokens the model can consider in one call — input and output (and, for some models, hidden thinking tokens). The model has no memory outside it: whatever you want it to use must be in the window on that call.

What consumes it

  • System instructions and policies of conduct
  • Tool / function definitions
  • Customer and reservation payload
  • Conversation history
  • Retrieved documents (RAG)
  • Tool outputs (grows with each call)
  • The new user message, plus reserved space for the answer and reasoning

Bigger is not automatically better

Long inputs cost more per call, run slower, and dilute attention: research on long-context models finds they use information at the start and end of a prompt more reliably than the middle. Some vendors also bill a premium above a token threshold. A tight, relevant prompt beats a bloated one.

What to pass to the model

The minimum sufficient set: the user request, the case-state summary, the top few reranked passages with source IDs, and trimmed tool results (the rows or fields that matter — not 10,000-row dumps). Everything else stays in a database the agent can query when needed.

Handling history

Keep the last N turns verbatim, replace older turns with a rolling summary, and pin durable facts (reservation ID, decisions made, promises to the customer) in the case-state object. Summarize with the lightweight model; never truncate a safety-relevant statement.

Why RAG helps, and multi-step limits

RAG sends a few kilobytes instead of the whole knowledge base. In agent loops, every tool call appends its output; after many steps the window fills with stale results. Fix with result trimming, summarizing completed sub-tasks, clearing old tool outputs, and caching the static prefix (system prompt + tool definitions).

5Execution, Guardrails, Evaluation & Human Escalation

What makes the system safe to run. The model proposes; deterministic code disposes.

Point 1

Execute through permissioned tools

  • Least privilege: the agent's tools only expose actions it is allowed to take, with credentials scoped to the end user and case.
  • Validate before acting: check schema, permissions, amount limits, account standing; require an idempotency key so a retry never refunds twice.
  • Sensitive actions: two-step (propose → verify → commit); above limits, require human approval.
  • UC1 is read-only: warehouse role with row-level security, query cost caps and timeouts.
Point 2

Guardrails: privacy, grounding, rules

  • PII: minimize what enters the prompt, redact in logs, mask in analytics outputs, enforce retention limits.
  • Hallucination prevention: answer only from retrieved evidence, require structured citations, verify numbers against the query result, allow "I don't know".
  • Deterministic rules own policy limits and eligibility; the LLM never decides an amount it was not given.
  • Confidence-based routing: low calibrated confidence → ask, investigate, or escalate.
  • Untrusted text (customer messages, host messages, web pages) is data, never instructions.
Point 3

Human-in-the-loop and fallback

Human-in-the-loop is designed in, not bolted on: explicit triggers, a full case file (summary, evidence, what was tried, recommended next action, reason for escalation), and a clean handoff so the customer never repeats themselves.

UC1: low-confidence or novel analyses are flagged "unverified — review by an analyst"; data owners get a feedback loop for wrong definitions.
UC2: human queues by specialty (safety, payments, account security); if tools or models fail, fall back to a human or a safe canned response — never silently drop the case.
Point 4

Monitoring and observability

Observability means every run is traceable: prompt version, retrieved chunks, tool calls and results, model, latency, cost, final answer, human override. Alert on drift: rising escalation rates, falling citation accuracy, tool error spikes, new unrecognized intents, latency and cost per resolution.

How to evaluate

Evaluation has three layers, each answering a different question.

Offline evaluation

Before launch and on every change: run a versioned golden dataset (real, de-identified questions/cases with expert-labelled answers, including hard and adversarial ones). Gate releases on thresholds per metric and per segment.

Online experimentation

Ship behind a flag and A/B test against the current flow, with guardrail metrics (CSAT, re-contact, safety misses). Start with shadow mode, then a small ramp. Choose the randomization unit carefully (e.g. customer, not message).

Continuous monitoring

Sample and grade live traffic (human + model-assisted graders), track drift dashboards, and feed failures back into the golden dataset. Every incident becomes a test case.

Prompt engineering, payload design and fine-tuning

Three different kinds of customization. They are not interchangeable.

Important distinction: editing a prompt or restructuring an API payload does not change the model — it changes the input. Fine-tuning is a training run that updates model weights using labelled examples. Calling prompt or schema changes "fine-tuning" is a common and costly mix-up.

Prompt engineering

  • System instructions and role
  • Business rules and tone
  • Few-shot examples of good answers and refusals
  • Output format requirements

Cheap, instant, reversible. Version prompts like code and test on the golden set.

Payload / input schema design

  • Structured JSON, consistent field names
  • Customer and reservation context
  • Trimmed conversation history
  • Retrieved passages with source IDs
  • Tool inputs/outputs; metadata and permissions

Good schema design improves accuracy and cuts tokens without touching the model.

Fine-tuning

  • Needed when a behavior can't be reached by prompting/RAG
  • Supervised fine-tuning for consistent classification or style
  • Small specialized models for high-volume narrow tasks

Needs hundreds–thousands of quality labelled examples, evaluation, and re-training when the world changes.

Architecture diagrams

Arrows show the direction of requests; colour shows what kind of work each box does. Scroll sideways on small screens.

Diagram A Internal Leadership Self-Service Chatbot

Read it as: ① leader asks → ② chat attaches identity → ③ light model extracts intent → ④ orchestrator plans and picks tools → ⑤ retrieval via RAG, SQL on the semantic layer, or MCP tools → ⑥ semantic-layer and SQL validation (approved metrics, read-only, cost limits) → ⑦ primary LLM synthesizes → ⑧ verification (numbers reconcile to the query result; citations support claims) → ⑨ answer with sources, lineage and metric definitions. Access control applies to every data touchpoint, not just the front door. Low-confidence or novel questions are flagged for an analyst.

Diagram B Customer Support AI Agent

Read it as: ①–② customer writes in an authenticated chat → ③ triage classifies intent and risk (high-risk cases take the dashed red direct route to specialists) → ④ orchestrator plans → ⑤ retrieves customer, booking, transaction and policy evidence → ⑥ decision engine combines business rules, LLM judgement and calibrated confidence → ⑦ one of four paths: A resolve through a validated tool call, B ask for missing information, C investigate further (bounded loop back to the orchestrator), D escalate with a full case file and the reason.

End-to-end examples

Step colours: retrieval reasoning tool execution validation escalation. All numbers are made up for illustration.

Example 1 "Why did customer support contact rates increase in India last month?"

  1. ReasonUnderstand. Light model parses: diagnostic "why" question; metric = contact rate; geography = India; period = last calendar month vs the month before. The metric's default definition comes from the catalog; ambiguity (per booking? per trip?) is resolved by default and stated in the answer, not by interrogating the leader.
  2. ValidateCheck access. Identity → role → allowed markets and metrics. India is in scope; PII columns are never exposed.
  3. RetrieveFetch definitions and context (RAG). Contact-rate definition and version, known incidents, policy or product changes dated in the window, release notes.
  4. ReasonPlan. (a) confirm the change vs baseline and normal variation; (b) split numerator (contacts) vs denominator (trips/bookings); (c) break down by contact reason, channel, language, guest vs host, city; (d) check data quality and pipeline delays; (e) line up with events.
  5. ExecuteGenerate queries on the semantic layer. The agent requests contact_rate by contact_reason × channel for both periods — it does not write free-form joins on raw tables.
  6. ValidateValidate and verify. Validator confirms approved metric/dimensions, read-only, partition filter, row cap. After execution: totals reconcile to the certified dashboard, freshness is within SLA, contributions sum to the total change, no sparse-segment artefacts.
  7. ReasonExplain. Illustrative result: contact rate rose from 8.0 to 9.2 per 1,000 trips (+1.2). Cancellation/refund-related contacts explain +0.7, payment issues +0.3, everything else +0.2; the rise is concentrated in one channel and two cities. The agent labels this as association and proposes the next check (e.g. compare against comparable markets before and after a suspected policy change) rather than asserting a cause.
  8. RespondAnswer with evidence. Summary, table/chart, metric definition and version, query ID, data as-of time, caveats, suggested follow-ups. The full trace is logged; low-confidence answers are flagged for analyst review.

Example 2 "I was charged twice for my reservation."

  1. ReasonIdentify intent. Triage labels it duplicate_charge, risk low, confidence high; the reservation is known from the session. No safety or fraud signal.
  2. RetrieveBooking and transaction details (APIs). Reservation status and total; payment ledger entries for this booking: how many, which are authorizations vs captures, amounts, timestamps, payment method.
  3. RetrievePolicy (RAG). Duplicate-charge and refund policy for the customer's region, current version, expected timelines. Top passages are reranked and cited.
  4. ReasonDecision engine. Rules evaluate the evidence, the LLM interprets edge cases, confidence is scored. Four possible outcomes:
Resolve — no action

The second entry is a temporary authorization hold that will drop off. Agent explains this, with the expected timeline.

Resolve — refund

Confirmed duplicate capture, same method and amount, within auto-refund limit, account in good standing. Validator passes → refund API with idempotency key → confirm and set expectations.

Ask / investigate

Amounts differ, split payment or currency conversion. Ask which charge looks wrong, or check processor status within a step limit.

Escalate

Amount above limit, chargeback already open, or fraud signal. Route to payments/trust specialists with the evidence, what was tried, and why the AI stopped.

  1. ValidatePre-action checks. Permissions, amount limit, no duplicate refund already issued, idempotency key; refund status is verified after the call.
  2. RespondClose the loop. Plain-language confirmation, case log, CSAT survey; later re-contact on the same booking is tracked as a failed resolution.
